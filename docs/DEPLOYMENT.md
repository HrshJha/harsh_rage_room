# Deploy with Render and Vercel

This is one repository with two independent deployment targets. Import the **repository root** in both services: the frontend imports shared contracts from `shared/`, and the API imports shared validation from the same directory. Vercel runs `npm run build:web` and publishes only `web/dist`; Render runs `npm run build:api` and starts only the Node API. Separate repositories, duplicated `shared/` files, and a second package tree are unnecessary. Render is needed when you want Telegram notifications; the frontend remains playable without API delivery.

## Render API

1. Push this repository to your Git provider. In Render, create a Blueprint from `render.yaml` at the repository root.
2. The Blueprint creates a Node web service and a private Key Value instance in Singapore. Both are explicitly on the free plan. Confirm current account availability before provisioning. No resources have been created by the local implementation.
3. Set `ALLOWED_ORIGINS` to the exact Vercel production origin, such as `https://your-project.vercel.app`. Use a comma-separated list for additional explicitly trusted preview origins; no wildcard subdomains.
4. Build: `npm ci --include=dev && npm run build:api`. Start: `npm start`. Health check: `/api/health`. The process binds `0.0.0.0` and Render's `PORT`.
5. `SESSION_HMAC_SECRET` is generated by the Blueprint. `REDIS_URL` uses the private Key Value connection string. Never copy these into Vercel variables.
6. Confirm `/api/health` responds with `{"ok":true,"notify":true,"mode":"dry-run"}`.

Free Render web services can sleep. The game keeps working while the API wakes or remains unavailable. Use an always-on service if the live tattle loop requires predictable latency. Free Key Value operational state can be lost on restart; use persistent paid Key Value if retaining counters/dedupe across service restarts matters. No analytics history is stored.

## Vercel frontend

1. Import the same repository. Keep the project root at the repository root. `vercel.json` sets Vite, the build command, and `web/dist`.
2. Set `VITE_API_BASE` to the Render API origin, without a trailing slash. It is public configuration, never a bot token.
3. For real notifications, create an hCaptcha widget for the exact production frontend hostname and set `VITE_HCAPTCHA_SITE_KEY` in Vercel. Supply its matching secret only in Render.
4. Redeploy after changing Vite variables; they are compiled at build time.
5. The supplied CSP permits `*.onrender.com`. If the API uses a custom domain, add that exact HTTPS origin to `connect-src` in `vercel.json`.
6. If sharing through a custom domain, confirm the absolute OG image URL. Vercel builds derive it from `VITE_SITE_URL`, `VERCEL_PROJECT_PRODUCTION_URL`, or `VERCEL_URL` in that order.

## Enable real Telegram

Set these **only on Render** (use Render’s secret environment fields; never commit `.env` or paste the token into source):

- `TELEGRAM_BOT_TOKEN`: your Chota Sher bot token.
- `TELEGRAM_CHAT_ID`: the destination chat that has already started the bot.
- `HCAPTCHA_SECRET`: the matching hCaptcha secret.
- `NOTIFY_DRY_RUN=false`.

Production refuses live-notification startup without bot, chat, HMAC, hCaptcha, and Redis configuration. Local development can send live with the bot token and destination chat ID in the ignored `.env` and `NOTIFY_DRY_RUN=false`; it uses in-memory rate limits and binds to `127.0.0.1`. The bot token was shared in chat, so rotate it through BotFather before relying on it for production. Outbound `sendMessage` does not change the bot's webhook or polling setup. The application does not call `setWebhook` or `getUpdates`.

Smoke-test one real named attack and one custom roast, checking name, action, exact roast text, and timestamp in Telegram. Also check anonymous entry and the final certificate. Then test `NOTIFY_ENABLED=false`; gameplay should remain available and the delivery indicator should report failure. Restore the switch after the check.

## Limits and rollback

The production API uses Redis atomic reservations for 10 sessions / 10 minutes per hashed IP key, 30 notify requests / 10 minutes, 60 notify requests / minute globally, and seven normal messages plus one final per session. Ordinary notifications are spaced five seconds apart. One send lock coordinates all API instances. Final bypasses only the per-session spacing. Telegram 429 responses determine retry delays. Development uses equivalent in-memory coordination.

Counters and dedupe keys expire; raw IPs and message contents are never logged. Delivery is best effort across network timeouts and restarts. A timeout after Telegram accepted a message can still result in a duplicate.

Use the hosting dashboards to roll back to the last verified deployment. `NOTIFY_ENABLED=false` is the immediate delivery kill switch. Git-based auto-deploy can be enabled after both projects and environment variables are connected.
